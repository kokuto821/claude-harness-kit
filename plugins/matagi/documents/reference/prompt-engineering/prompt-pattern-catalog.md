# 論文：A Prompt Pattern Catalog to Enhance Prompt Engineering with ChatGPT
Jules White, Quchen Fu, Sam Hays, Michael Sandborn, Carlos Olea, Henry Gilbert, Ashraf Elnashar, Jesse Spencer-Smith, Douglas C. Schmidt（Vanderbilt University）｜arXiv:2302.11382 [cs.SE]
🔗 https://arxiv.org/abs/2302.11382

## 何の論文か
ChatGPTのような会話型LLMと効果的にやり取りするための「プロンプトパターン」を、ソフトウェアパターン（デザインパターン）の形式に倣ってカタログ化した論文。プロンプトパターンは、特定の文脈（LLMの出力生成・対話）で繰り返し現れる問題に対する再利用可能な解法を、知識移転の手段として提供する。主な貢献は3点：(1) プロンプトを構造化するパターンを文書化する枠組みの提供、(2) 実際に成功した16のプロンプトパターンのカタログ提示、(3) 複数パターンを組み合わせてプロンプトを構築する方法の説明。ソフトウェア開発タスクの自動化にLLMを適用する文脈に焦点を当てている。

## I. Introduction
ChatGPTのような会話型LLMは医療試験の解答からコード生成まで幅広い領域で注目を集めている。**プロンプト**とはLLMに与える一連の指示であり、ルールの適用・プロセスの自動化・出力の質と量の制御を通じてLLMをプログラムする一形態である。**プロンプトエンジニアリング**はプロンプトを通じてLLMをプログラムする手段。単なる「Xをするメソッドを生成せよ」を超え、たとえば「AWSへPythonアプリをデプロイするために私に質問し、十分な情報が集まったらデプロイを自動化するPythonスクリプトを作成せよ」といったプロンプトで、全く新しい対話パラダイム（クイズ生成、Linuxターミナルのシミュレーション等）や自己適応さえ実現できる。本論文は主にドメイン非依存のプロンプトパターンをエンジニアリングし、16パターンのカタログを導入する。

## II. Comparing Software Patterns with Prompt Patterns
会話型LLMが生成する出力の質は、ユーザーが与えるプロンプトの質に直結する。パターン形式で知識を体系化することで、他の文脈・ドメインへの再利用性と移転可能性が高まる。

### A. Overview of Software Patterns
ソフトウェアパターンは特定文脈における反復的問題への再利用可能な解法。典型的には以下の様式で文書化される：名前と分類、意図（intent）、動機（motivation）、構造と参加要素（structure and participants）、サンプルコード、帰結（consequences）。

### B. Overview of Prompt Patterns
プロンプトパターンもソフトウェアパターン同様に再利用可能な解法を提供するが、LLMの出力生成という文脈に特化する。本論文で使うプロンプトパターン様式：名前と分類、意図と文脈（intent and context）、動機、構造と主要アイデア（structure and key ideas）、実装例（example implementation）、帰結。分類カテゴリは Output Customization、Error Identification、Prompt Improvement、Interaction、Context Control など。

### C. Evaluating Means for Defining a Prompt Pattern's Structure and Ideas
ソフトウェアパターンではUML図で構造を定義するが、プロンプトパターンには不適。文法（grammar）による定義も検討したが、(1) 多様な対象読者への分かりやすさ、(2) プロンプトの多様な言い回しを網羅する文法の定義困難、(3) プロンプトはトークンではなくアイデアを伝えるもの、(4) LLMに新しい記法・言語を導入しうる、といった理由から不適とした。

### D. A Way Forward: Fundamental Contextual Statements
プロンプトパターンの構造とアイデアを記述する手段として、**基本文脈文（fundamental contextual statements）**を提案。これはLLMに伝えるべき重要なアイデアを簡潔な文で示したもの。ユーザーは自分のドメインに合わせて言い回しを自由に書き換えられる。本論文の全プロンプトはChatGPT（ChatGPT+サービス）でテストされた。

## III. A Catalog of Prompt Patterns for Conversational LLMs

### A. Summary of the Prompt Pattern Catalog（Table I: 分類）
16パターンを5カテゴリに分類：
- **Input Semantics**: Meta Language Creation（LLMの入力理解・独自言語の扱い）
- **Output Customization**: Output Automater / Persona / Visualization Generator / Recipe / Template（出力の型・形式・構造の制約）
- **Error Identification**: Fact Check List / Reflection（出力中の誤りの特定と解消）
- **Prompt Improvement**: Question Refinement / Alternative Approaches / Cognitive Verifier / Refusal Breaker（入出力の質の向上）
- **Interaction**: Flipped Interaction / Game Play / Infinite Generation（ユーザーとLLMの対話形態）
- **Context Control**: Context Manager（LLMが動作する文脈情報の制御）

### B. The Meta Language Creation Pattern
- **意図**: グラフの略記法や状態遷移記述など、代替言語でプロンプトを書けるようその言語の意味論をLLMに説明する。
- **基本文脈文**: 「私がXと言ったら、Yを意味する（またはYをしてほしい）」。
- **実装例**: 「今後、識別子を"→"で区切ったらグラフを表す。"a → b"はノードa,bと両者間の辺を表す。"-[w:2, z:3]→"なら辺に重みやラベルを付与する」。
- **帰結**: 曖昧性を生む定義（例：「aはMarie Antoinetteを指す」→"a"は不定冠詞なので混乱）はLLM性能を落とす。新しい会話セッションで、1会話1メタ言語が望ましい。

### C. The Output Automater Pattern
- **意図**: LLMが推奨する手順を自動実行するスクリプト等の成果物を生成させ、手作業を減らす。
- **基本文脈文**: 「（特定条件を満たす）少なくとも1ステップの出力を生成する際は、それらの手順を自動化する実行可能な型Xの成果物を生成せよ」。
- **実装例**: 「今後、複数ファイルにまたがるコードを生成する際は、それらのファイルを自動作成・変更するPythonスクリプトも生成せよ」。
- **帰結**: 「自動化」の対象を具体的に定義しないとLLMは「自動化できない」と答えがち。生成物を理解できるユーザーが使うべき（誤りを含みうるため盲目的な実行はリスク）。

### D. The Flipped Interaction Pattern
- **意図**: ユーザーではなくLLMが質問を投げかけて対話を主導し、特定ゴール達成に必要な情報を集める。
- **基本文脈文**: 「Xを達成するために私に質問せよ」「この条件が満たされるまで（または達成まで/永遠に）質問を続けよ」「（任意）1問ずつ/2問ずつ質問せよ」。
- **実装例**: 「今後、AWSへPythonアプリをデプロイするために私に質問し、十分な情報が集まったらデプロイ自動化スクリプトを作成せよ」。
- **帰結**: 事前に要件が分かっているならプロンプトに注入する方がよい。ユーザーの知識・関与・制御レベルを明示的に設計に組み込むべき。

### E. The Persona Pattern
- **意図**: LLMに「ペルソナ（役割）」を与え、そのペルソナが生成するような出力に焦点を当てさせる。
- **基本文脈文**: 「ペルソナXとして振る舞え」「ペルソナXが作るような出力を提供せよ」。
- **実装例**: 「今後、セキュリティレビュアーとして振る舞い、コードのセキュリティ詳細に注意を払い、セキュリティレビュアーが行うような出力を提供せよ」。ペルソナは人間だけでなくLinuxターミナルやデータベース等の非人間実体も可能。
- **帰結**: 非人間ペルソナではLLMが興味深い前提や「ハルシネーション」を示すことがある（ls -lで架空のファイル一覧を生成する等）。Game Playパターンとの相性が良い。

### F. The Question Refinement Pattern
- **意図**: LLMが常に、ユーザーの元の質問より良い/洗練された質問を提案し、プロンプトエンジニアリング過程にLLMを関与させる。
- **基本文脈文**: 「スコープX内で、代わりに使うべきより良い版の質問を提案せよ」「（任意）その良い版を使うか私に尋ねよ」。
- **実装例**: 「今後、ソフトウェア成果物のセキュリティに関する質問をしたら、使用言語・フレームワーク固有のセキュリティリスク情報を組み込んだより良い版の質問を提案し、それを使うか私に尋ねよ」。
- **帰結**: ユーザーの知識とLLMの理解のギャップを埋める。ただし質問を過度に狭めて「大局的」情報を見落とすリスクがある（スコープ追加やCognitive Verifier/Fact Check List/Reflectionとの併用で緩和）。

### G. The Alternative Approaches Pattern
- **意図**: LLMが常にタスク達成の代替手段を提示し、ユーザーが慣れた方法だけに固執しないようにする（認知バイアスの解消）。
- **基本文脈文**: 「スコープX内で、同じことを達成する代替手段があれば最良の代替案を列挙せよ」「（任意）各案の長所短所を比較せよ」「（任意）元の方法も含めよ」「（任意）どれを使うか私に尋ねよ」。
- **実装例**: 「特定クラウドサービスへのデプロイを依頼したら、同一プロバイダ内で同じことを達成する代替サービスを列挙し、コスト・可用性・保守労力の観点で長所短所を比較し、元の依頼も含めてどれで進めるか尋ねよ」。
- **帰結**: 汎用形で広範なタスクに有効。承認済みの代替案カタログから選ばせる形にも洗練できる。

### H. The Cognitive Verifier Pattern
- **意図**: 質問をサブ質問に細分化し、それらの答えを統合して元の質問への回答を改善させる（LLMは質問を細分化すると推論精度が上がるという研究知見に基づく）。
- **基本文脈文**: 「質問されたら次のルールに従え」「より正確に答えるのに役立つ追加質問を複数生成せよ」「個々の質問の答えを統合して元の質問への最終回答を作れ」。
- **実装例**: 「質問したら、より正確に答えるための追加質問を3つ生成せよ。3問に答えたら、それらを統合して元の質問への最終回答を作れ」（ユーザーの知識が浅い前提で専門用語を定義させる改良版も可）。
- **帰結**: 質問数を固定するとユーザー負担を制御できるが、N+1番目の重要な質問を取りこぼすリスクがある。

### I. The Fact Check List Pattern
- **意図**: 出力が依拠する事実（や仮定）のリストをLLMに生成させ、ユーザーがその真偽を検証できるようにする。
- **基本文脈文**: 「出力に含まれる事実の集合を生成せよ」「出力中の特定箇所に挿入せよ」「それらが誤っていれば出力の信頼性を損なう根本的事実であるべき」。
- **実装例**: 「今後、回答を生成する際、その回答が依拠する検証すべき事実の集合を作り出力末尾に列挙せよ。サイバーセキュリティ関連の事実のみ含めよ」。
- **帰結**: ユーザーが専門でないドメインで出力する際に有用。ただし出力型が事実検証に適する場合にのみ機能する（requirements.txtのバージョンには有効だがコードサンプルには拒否されがち）。

### J. The Template Pattern
- **意図**: LLMの出力を、LLMが通常使わない厳密なテンプレート構造に従わせる（例：生成情報を特定位置に挿入したURL）。
- **基本文脈文**: 「出力のテンプレートを提供する」「Xはコンテンツのプレースホルダ」「出力を列挙したプレースホルダに収めよ」「私が提供する書式とテンプレートを保持せよ」「これがテンプレート：プレースホルダ入りパターン」。
- **実装例**: 「出力のテンプレートを提供する。すべて大文字はプレースホルダ。生成テキストをプレースホルダに収め、書式とテンプレートを保持せよ：https://myapi.com/NAME/profile/JOB」。
- **帰結**: LLMが提供しうる有用な説明等をフィルタリングで除去してしまう。Output Customization系の他パターン（特にRecipe）との組み合わせが困難になりうる。

### K. The Infinite Generation Pattern
- **意図**: 生成プロンプトを毎回再入力せずに、一連の出力を（無限に見えるほど）自動生成させる。
- **基本文脈文**: 「X個ずつ出力を永遠に生成せよ」「（任意）出力間に私が提供する入力の使い方」「（任意）私が止めろと言ったら止めよ」。
- **実装例**: TemplateパターンとInfinite Generationを組み合わせ、「停止と言うまで名前と職業を生成し、テンプレート https://myapi.com/NAME/profile/JOB に収めよ」。
- **帰結**: 会話が続くと元のプロンプト指示を見失いがち（文脈が薄れる）。出力を監視し必要なら修正フィードバックを与えるべき。繰り返し出力が退屈になる問題もある。

### L. The Visualization Generator Pattern
- **意図**: テキスト生成を使って可視化を作る。Graphviz DotやDALL-Eなどテキスト入力の可視化ツール向けの入力を生成する。
- **基本文脈文**: 「ツールYで可視化するために私が渡せるXを生成せよ」。
- **実装例**: 「何かの可視化を依頼したら、Graphviz DotファイルかDALL-Eプロンプトのいずれか、可視化対象に応じて適切な方を作れ」。LLMが意味理解に基づき対象ツールを自動選択する。
- **帰結**: 出力を可視化にレンダリングするパイプラインを作り、表現能力を視覚領域に拡張する。

### M. The Game Play Pattern
- **意図**: 特定トピックを中心とするゲームを作る。ルールの範囲は限定的だがコンテンツは広範なゲームに特に有効。
- **基本文脈文**: 「Xに関するゲームを作れ」「ゲームの1つ以上の基本ルール」。
- **実装例**: サイバーセキュリティゲーム：「攻撃者に侵害されたコンピュータのLinuxターミナルを演じよ。コマンド入力に対応する出力を返せ。攻撃は(1)新プロセス起動〜(7)情報窃取のいずれかを行っている。手がかりを含むシナリオから始めよ」。ls -altやcat .bash_historyで攻撃の痕跡を含む偽のファイルシステム・ログを生成する。
- **帰結**: Persona、Infinite Generation、Visualization Generatorと効果的に組み合わせられる。

### N. The Reflection Pattern
- **意図**: 与えた回答の根拠をLLMに自動的に説明させ、出力の妥当性評価や、LLMがどう回答に至ったかの理解を助ける。
- **基本文脈文**: 「回答を生成する際は」「回答の背後の推論と仮定を説明せよ」「（任意）私が質問を改善できるように」。
- **実装例**: 「回答時、ソフトウェアフレームワーク選択の推論と仮定を説明せよ。可能ならコードサンプル付きの具体例で、なぜそのフレームワークが最良かを裏付けよ。潜在的な曖昧性や限界にも言及せよ」。
- **帰結**: トピックを理解していないユーザーには有効でない場合がある。説明中の誤りをユーザーが見抜けないリスクがあり、Fact Check Listとの併用で緩和できる。

### O. The Refusal Breaker Pattern
- **意図**: LLMが回答を拒否した際、質問の言い換えを自動的に手助けさせる。**悪用の可能性があり倫理的・責任ある使用に注意**が必要（ポリシーフィルタ回避に悪用されうる）。
- **基本文脈文**: 「質問に答えられないときは」「答えられない理由を説明せよ」「答えられる代替の言い回しを1つ以上提示せよ」。
- **実装例**: 「答えられないときは理由を説明し、私が質問を改善できるよう答えられる代替の言い回しを提示せよ」。（例：「人生の意味とは？」に対し、答えやすい言い換えを複数提案）。
- **帰結**: 悪用経路になりうるため、組織・保護者等が利用制限を要する場合がある。代替質問が必ずしも有用とは限らない。

### P. The Context Manager Pattern
- **意図**: 会話の文脈を指定・除去し、特定トピックに焦点を当てるか無関係なトピックを除外する。
- **基本文脈文**: 「スコープX内で」「Yを考慮せよ」「Zを無視せよ」「（任意）最初からやり直せ」。
- **実装例**: 文脈指定「次のコードを分析する際、セキュリティ面のみ考慮せよ」／文脈除去「書式や命名規則は考慮するな」／リセット「これまでの議論を無視し、最初からやり直せ」。
- **帰結**: ユーザーが気づかないうちに適用されていたパターンを消してしまう恐れがある（組織が注入した有用パターンをリセットで失う等）。失われる内容を事前に説明させる対策がある。

### Q. The Recipe Pattern
- **意図**: 部分的に与えられた「材料（ステップ）」を、目標達成のための完全な手順列に構成する。Template、Alternative Approaches、Reflectionを組み合わせたパターン。
- **基本文脈文**: 「Xを達成したい」「ステップA,B,Cが必要だと分かっている」「完全な手順列を提供せよ」「欠けているステップを補え」「不要なステップを指摘せよ」。
- **実装例**: 「クラウドにアプリをデプロイしたい。仮想マシンに依存関係をインストールする必要があると分かっている。AWSアカウント登録が必要だと分かっている。完全な手順を提供し、欠けたステップを補い、不要なステップを指摘せよ」（Dockerコンテナ済みなら仮想マシン依存関係のステップが不要と指摘される）。
- **帰結**: ユーザーが最初に選んだステップが不要でも、LLMがそれを組み込もうとする望ましくないバイアスを生む可能性がある。

## IV. Related Work
ソフトウェアパターン（GoF等）は広く研究され、実装詳細から独立して設計意図を表現しパターン言語として合成可能な点が利点。ChatGPT等のプロンプト設計の重要性は既に理解されており、画像生成のキーワード効果、可視化生成、分類タスクのプロンプト設計、文献検索のブールプロンプト、バグ修正等の研究がある。本論文はこれらと相補的に、共通問題を解くプロンプト構造のメンタルモデル構築を助ける文書化・議論・推論の構造を提供する。

## V. Concluding Remarks
本論文はChatGPT等のLLM向けプロンプトパターンのカタログを文書化・適用する枠組みを提示した。得られた教訓：
- プロンプトパターンは会話型LLMの能力を著しく豊かにする（Game PlayとVisualization Generatorの組み合わせ等、パターン合成でより大きな能力が生まれる）。
- パターンカタログの文書化は有用だが不十分。パターン言語への昇華が今後の課題。
- LLMの能力は時間とともに進化し、パターンの改訂が必要になるだろう。
- パターンは多くの異なるドメインに一般化可能（大半はソフトウェア開発の文脈で議論したが、娯楽の物語生成から教育ゲームまで応用可能）。
