# 論文 - A Survey of Context Engineering for Large Language Models
原文：https://arxiv.org/abs/2507.13334

# 要旨
大規模言語モデル（LLM）の性能は、推論時に与えられるコンテキスト情報によって根本的に決定されます。本調査では、単なるプロンプト設計の枠を超え、LLMのための情報ペイロードを体系的に最適化する学問分野として「コンテキストエンジニアリング（Context Engineering）」を提唱します。

私たちは、コンテキストエンジニアリングをその基礎的な構成要素と、それらをインテリジェントなシステムに統合するための高度な実装手法へと分解し、包括的な分類体系を提示します。まず、コンテキストの「取得と生成」「処理」「管理」という基礎的な構成要素を精査します。続いて、これらの要素がどのようにアーキテクチャとして統合され、検索拡張生成（RAG）、メモリシステム、ツール統合型推論、マルチエージェントシステムといった高度なシステム実装が構築されるのかを解説します。

1400本以上の研究論文を体系的に分析した本調査は、この分野の技術的なロードマップを確立するだけでなく、重要な研究上のギャップを明らかにしました。それは、モデルの能力間に根本的な非対称性が存在するという点です。高度なコンテキストエンジニアリングによって補強された現在のモデルは、複雑なコンテキストを理解する能力においては目覚ましい習熟度を示していますが、それと同程度に高度な長文を出力する能力には顕著な限界があります。このギャップに対処することが、今後の研究における最優先事項です。

結論として、本調査はコンテキストを意識したAIの発展を目指す研究者とエンジニアの双方に向けて、統一されたフレームワークを提供します。

# 本文
## 1. Introduction
LLMの性能は受け取るコンテキストに根本的に規定される、という前提から出発。研究領域が「断片化」して個別に進んでいる現状を問題視し、それらを横断する統一タクソノミーを初めて提示するのが本サーベイの主眼。基盤コンポーネント（検索・生成／処理／管理）と、その上に構築される実装（RAG／メモリ／ツール統合推論／マルチエージェント）に区分する枠組みを宣言する。

## 2. Related Work
既存サーベイは「プロンプトエンジニアリング」「RAG」「メモリ」など特定の垂直領域に閉じていると指摘。本サーベイは、それらを縦割りではなく水平（horizontal）に貫く統一タクソノミーを提供し、基盤要素と複合システムの橋渡しをする点で差別化されると位置づける

##  3. Why Context Engineering?（なぜコンテキスト工学か）
LLMが単なる指示追従から複雑なアプリの「頭脳」へ進化した以上、「プロンプトを工夫する」だけでは足りない、というのが出発点です。
### 3.1 定義
この章はまず「LLMとは何をしている機械か」を1本の式で表します。

式(1)： Pθ(Y | C) = ∏ₜ Pθ(yₜ | y₍<ₜ₎, C)

読み方は「モデル（パラメータθ）は、コンテキスト C を受け取って、出力 Y を1語ずつ順に生成する。各語 yₜ は、それまでに出した語と C の両方に条件づけられて決まる」。要するに 出力の質は C 次第 という当たり前の事実を式にしただけです。従来のプロンプト工学は、この C を「一枚の固定した文字列（C = prompt）」とみなしていました。
コンテキスト工学は、その C を作り直します。

式(2)： C = A(c₁, c₂, …, cₙ)

「コンテキスト C は、複数の情報部品 c₁…cₙ を、組立係 A がまとめ上げて作るもの」という意味です。部品は6種類に整理され、それぞれが本サーベイの各章に対応します：

c_instr … システム指示・ルール（4.1）
c_know … 外部知識（RAG、4.2・5.1）
c_tools … 使えるツールの定義（5.3）
c_mem … 過去の対話から引き継ぐ記憶（4.3・5.2）
c_state … ユーザーや世界、エージェント系の現在の状態（5.4）
c_query … ユーザーの今の要求

次に「では何を目指すのか」を式にします。

式(3)： F* = arg max_F E₍τ∼T₎[ Reward( Pθ(Y | C_F(τ)), Y*_τ ) ]　（制約：|C| ≤ L_max）

記号が多いですが、言いたいのは一つ——"部品の集め方・選び方・並べ方"の一式（F）を、いろいろなタスク τ にわたって平均的に一番良い答えが出るように選ぶ。それが最適な設計 F* 。Reward は出力の良さの採点、Y* は理想の答え、E[…] は「多数のタスクにわたる平均」の意味です。そして |C| ≤ L_max は 「コンテキストの長さには上限がある」という現実の制約 を表します。ポイントは、最適化の対象が個々のプロンプト文ではなく "組み立て方そのもの" に移っている点です。
さらに理論的な見方が3つ添えられます（いずれも根っこは同じ主張の言い換えです）。
まず組立係 A の中身：

式(補)： A = Concat ∘ (Format₁, …, Formatₙ)

「各部品をモデルに合った形に整形（Format）してから、つなぎ合わせる（Concat）パイプライン」という意味で、A は魔法ではなく整形と連結の手続きだと明示しています。
次に知識検索の目標：

式(4)： Retrieve* = arg max_Retrieve I( Y* ; c_know | c_query )

I(・;・) は「相互情報量」＝二つのものがどれだけ深く関係しているかの尺度。つまり 「取ってくる知識は、ただ質問文と似ているものではなく、"理想の答え Y* に一番効く"ものを選ぶべき」 という主張です。
最後に不確実性の扱い：

式(5)： P(C | c_query, …) ∝ P(c_query | C) · P(C | History, World)
式(6)： C* = arg max_C ∫ P(Y | C, c_query)·Reward(Y, Y*) dY · P(C | c_query, …)

これはベイズの考え方で、「唯一の正しいコンテキストを決め打ちするのではなく、"どのコンテキストがもっともらしいか"を確率的に推論し、期待される報酬が最大になるものを選ぶ」 という枠組みです（∝ は「比例する」、∫…dY は「起こりうる答えを平均する」意味）。多段推論で信念を更新しながら適応的に検索を調整できる、という利点につながります。
これらを通じた3.1の主張は一言でいえば——コンテキスト作りを、勘や"芸術"ではなく、体系的な工学（＝情報の物流とシステム最適化の科学）として扱おう、ということ。表1では、プロンプト工学（静的・状態を持たない・手作業で改良）とコンテキスト工学（動的・状態を持つ・システムとして最適化）が対比されます。
最後に「コンテキストのスケーリング」を2方向で捉えます。ひとつは長さ方向（数千語→数百万語へ）、もうひとつは種類・構造方向（テキストだけでなく、時間・空間・登場人物の状態・意図・文化まで）。
### 3.2 なぜ必要か

#### 3.2.1 
現状の限界 — 入力が長くなると計算量が急激に膨らむ（長さが2倍で手間は約4倍、という二次的な増え方）。これがコスト・遅延の壁になる。加えて幻覚、入力への不忠実さ、言い回しの変化への過敏さ、見た目は正しいが中身の薄い応答といった信頼性の問題。
#### 3.2.2 
性能向上 — RAGや段階的推論（Chain-of-Thought）でナビゲーション精度が18倍、コード要約やバグ修正で大幅改善など、工夫次第で実測の効果が大きい。
#### 3.2.3 
リソース最適化 — 必要な情報だけを賢く絞ることで、少ないトークンで同等の品質を出せる。関連情報が一部欠けても、文脈の手掛かりと事前知識で妥当な答えを出せる特性も活用。
#### 3.2.4 
将来性 — 再学習なしで、例を見せるだけで新タスクに適応できる（in-context learning）。段階的推論や計画立案と組み合わせ、文脈を理解するアプリの土台になる。

## 4. Foundational Components（基盤コンポーネント）
コンテキストの「素材」を扱う3つの層です。
### 4.1 検索・生成 — 良い指示文をどう作り、外部知識をどう取ってきて、どう組み立てるか。

### 4.1.1 
プロンプト工学：段階的に考えさせるCoT（「順を追って考えよう」の一言で正答率が大きく上がる例あり）、それを木構造や網目構造に拡張したToT・GoT、人間の思考手順を模した認知的プロンプト。自分の出力を自分で直すSelf-Refine系の手法一覧。
### 4.1.2 
外部知識検索：RAGの基本（モデル内部の知識＋外から取ってくる知識の併用）、検索するかどうかを自分で判断するSelf-RAG、ナレッジグラフとの統合。
### 4.1.3 
動的な組立：部品をテンプレートや優先度で並べる、表やDBを自然な文章に変換する、あるいは逆にKGはPython・DBはSQLといったプログラム表現で渡すと複雑な推論では有利、自動でプロンプトを改良する手法。

### 4.2 
処理 — 集めた情報を使いやすく整える層。

### 4.2.1 
長文処理：長い入力ほど計算が重くなる問題への対策。効率的な新アーキテクチャ（Mamba等）、位置情報の調整で窓を広げる技術（YaRN、LongRoPEで200万語級）、注意計算やメモリの効率化（FlashAttention、StreamingLLM等)。
### 4.2.2 
自己精緻化と適応：出力→自己評価→改良を繰り返すSelf-Refineやリフレクション、自分で改善方法を編み出す手法、じっくり長く考えるLong CoT（o1、DeepSeek-R1など）。
### 4.2.3 
マルチモーダル：画像・音声・3Dの統合。特定モダリティに偏るバイアスや、良質データ・計算資源の不足が課題。
### 4.2.4 
関係・構造化データ：表・DB・KGは、そのまま一列に並べると関係性が失われる。グラフ埋め込みやグラフニューラルネットで構造を保つ。

### 4.3 
管理 — 有限なコンテキスト窓をやりくりする層。

### 4.3.1 
根本的制約：窓の有限性、長文中盤の情報が抜け落ちる「lost-in-the-middle」現象、LLMが毎回の対話を独立に処理する"記憶を持たない"性質、窓超過による忘却や文脈の混線。
### 4.3.2 
記憶アーキテクチャ：OSの仮想メモリのように内部と外部を出し入れするMemGPT、忘却曲線を模して重要度で記憶を増減させるMemoryBankなど。
### 4.3.3 
圧縮：長い文脈を小さな"要約枠"に畳み込む（4分の1に圧縮する例など）技術。

## 5. System Implementations（システム実装）
素材を組み合わせた4つの完成形アーキテクチャです。
### 5.1 
RAG — 外部知識を検索して生成に活かす仕組み。部品を柔軟に組み替えるモジュラーRAG、自律エージェントが検索戦略を動的に決めるエージェント的RAG、ナレッジグラフで多段の関係をたどるグラフ強化RAG、本番向けのリアルタイム・低遅延RAG。
### 5.2 
メモリシステム — 毎回リセットされるLLMに永続的な記憶を持たせ、学習・適応するエージェントに変える。短期記憶と長期記憶の階層、記憶の分類方式。評価ベンチマークLongMemEvalでは、商用アシスタントでも長い対話の中で精度が30%落ちることが示されている。
### 5.3 
ツール統合推論 — 「文章を書くだけ」から「世界に働きかける」存在へ。関数呼び出し（Toolformer、ReAct等）、推論と外部ツールを噛み合わせるTIR、強化学習で最適なツールの使い方を自分で見つける手法（ReToolがAIME2024で67.0%達成など）。
### 5.4 
マルチエージェント — 複数エージェントの連携。通信プロトコル（「AIのUSB-C」と呼ばれるMCP、A2A、ACP）、誰にどう仕事を割り振るかのオーケストレーション、そして協調の難所（処理の一貫性保証の不足、LLMの自己検証頼みの危うさ、依存関係の不透明さ）。
## 6. Evaluation（評価）
多くの部品が動的に絡むため、従来のLLM評価では不十分、という問題意識。
### 6.1 
部品を単独で測る評価（例：長い文書に紛れた一文を見つけられるか＝needle in a haystack）と、システム全体を最終タスクで測る評価。部品を組み合わせたときに生まれる相乗効果や、逆に足を引っ張り合う干渉も捉える必要がある。
### 6.2 
長文処理向け、RAG向け、ツール利用向け（Berkeley Function Calling Leaderboardが2,000ケースで測定）などのベンチマーク群。
### 6.3 
BLEUやROUGEといった古い指標では複雑な推論を測れないこと、多部品システムでは不具合の原因特定が難しいこと、そして単発でなく"改良を繰り返す中でどれだけ賢く学ぶか"を測る新しい評価、安全性・頑健性の評価が必要、と指摘。
## 7. Future Directions and Open Challenges（今後の課題）
孤立した部品開発から統合システムへ移るほど課題が複雑になる、という認識で今後10年の論点を整理。
### 7.1 
散在する技術を束ねる統一理論がまだ無いこと、スケーリングと効率、マルチモーダル統合。
### 7.2 
transformerを超える次世代アーキテクチャ、より深い推論・計画、複雑な文脈の構造化、コンテキストの組み立てを自動・知的に最適化すること。
### 7.3 
ドメイン特化、数百〜数千エージェントの大規模協調（通信プロトコルの標準化はまだ脆弱性やスケール制約あり）、人間とAIの協働。
### 7.4 
本番展開のスケーラビリティと信頼性、安全性・セキュリティ、倫理と責任ある開発。
### 8. Conclusion
統一タクソノミーの提示が主要貢献。最重要の発見として、「理解-生成ギャップ（comprehension-generation gap）」 を強調する——現在のモデルは高度なコンテキスト工学によって複雑な文脈の理解には長けるが、同等に洗練された長文生成には顕著な限界がある、という非対称性が今後の最優先課題だと結論づけている。加えて、複数技術の相乗統合、モジュール性・合成可能性への潮流を指摘。
