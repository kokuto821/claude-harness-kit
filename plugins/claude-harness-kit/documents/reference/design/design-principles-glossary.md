# 設計原則・法則 用語集（glossary）

参考：https://qiita.com/miruky/items/cef8169b4a10cdd790b5#2-2-%E5%90%8D%E8%91%97%E3%81%A7%E3%82%88%E3%81%8F%E8%A6%8B%E3%82%8B%E9%96%8B%E7%99%BA%E6%89%8B%E6%B3%95%E3%81%A8%E6%AF%94%E5%96%A9

設計・開発で参照される法則・原則・比喩の用語集。各項目は簡潔な定義に留める参照資料。

コード設計の中核原則（DRY・SRP・関心の分離・疎結合/高凝集）の**定義と判断基準は、用語集ではなくルール側の [[design-rule]]（`rules/design-principles/design-rule.md`）を唯一の正**とする。本ファイルは、それらを取り巻く周辺法則の意味を引くためのリファレンス。中核4原則の判断基準はここで再掲しない。

## 設計とコードの法則

デメテルの法則：オブジェクトは近い相手だけを知るべき、という設計原則です。最小知識の原則とも呼ばれます。

漏れ出す抽象化の法則：どんな抽象化も、どこかで下層の事情が漏れる、という法則

カーニハンの法則：デバッグはコードを書くより難しい。だから、賢すぎるコードを書くと自分でも直せなくなる、という法則です。

## 指標と意思決定の法則

パレートの法則：結果の多くは少数の原因から生まれやすい。80対20の法則とも呼ばれます。

マーフィーの法則：「失敗しうることは失敗する」。「失敗するはずがない」ではなく、「失敗したらどう安全に止めるか」を考えるための言葉です。

グッドハートの法則：指標が目標になると、その指標は良い指標でなくなる、という法則です。

## 周辺の設計原則

KISS：Keep It Simple, Stupidの略で、できるだけシンプルにする、という原則です

YAGNI：You Aren't Gonna Need Itの略で、まだ必要でない機能は作らない、というExtreme Programming（XP）由来の原則です。

SOLID：オブジェクト指向設計でよく語られる5原則の頭文字です。単一責任の原則、開放閉鎖の原則、リスコフの置換原則、インターフェース分離の原則、依存性逆転の原則をまとめたものです。単一責任の原則の定義は [[design-rule]] に従う。

最小権限の原則：必要最小限の権限だけ与える、というセキュリティ原則です。

開放閉鎖の原則：拡張には開き、既存修正には閉じる

最小驚きの原則：利用者が驚かない挙動にする、という原則

UNIX哲学：小さく作り、うまく組み合わせる、というUnix文化の設計思想です。「一つのことをうまくやる」「テキストストリームでつなぐ」「小さなツールを組み合わせる」といった考え方が代表的です。

WET：DRYの逆を表す言葉です。よくない状態を表します。同じ処理、同じルール、同じ設定をあちこちに書いている状態です。

ETC（変更しやすさ）：Easier to Changeの略で、変更しやすさを設計判断の中心に置く、という考え方です。

## 名著でよく見る開発手法と比喩

車輪の再発明：既にあるものを無駄に作り直す、という比喩です。ライブラリや標準機能を調べずに、自作フレームワークや自作暗号を作ってしまうような場面で使われます。ただし、学習目的や制約が明確な場合の再実装には価値があります。問題なのは、既存の知見を無視して同じ失敗を繰り返すことです。

ゆでガエル：少しずつ悪化すると、人は危険に気づきにくい、という比喩です。水を少しずつ温められたカエルが危険に気づけない、という寓話的な説明から、ゆっくり進む劣化への鈍感さを表す言葉として使われます。

割れ窓理論：小さな荒れを放置すると、さらに荒れる、という理論です。

銀の弾丸はない：ソフトウェア開発の本質的な難しさを一撃で消す技術はない、というフレデリック・ブルックスの有名な主張です。

トレーサーバレット（曳光弾）：最初から本番に近い細い縦切りを通す、という考え方です。本番に向かう細い実装として扱います。

## 認知と学習の比喩

ジョシュアツリーの法則：名前を知ると、それまで見えていなかったものが見えるようになるという比喩

確証バイアス：自分の仮説に合う情報だけを集めやすい、という認知バイアスです。仮説を立てるのは大事ですが、反証するログも見る必要があります。

オッカムの剃刀：複数の説明が同じくらい成り立つなら、必要以上に仮定を増やさない、という考え方です。「必要なしにものを増やしてはいけない」という単純性の原理として知られ、余計な仮説を剃刀で削ぎ落とす、という比喩で語られます。障害調査で、いきなり複雑な分散システムのバグを疑う前に、設定ミス、環境変数、デプロイ漏れ、入力値、タイムゾーンのような単純な原因を確認します。

チェスタトンの柵：なぜ存在するかわからないものを、理解する前に壊してはいけない、という考え方です。意味不明な if 文や謎の設定を見つけたとき、すぐ消したくなります。しかし、そのコードが過去の障害対応や顧客個別要件の名残かもしれません。消す前に、ログ、Issue、コミット履歴、担当者の記憶を確認します。

## アーキテクチャと分散システムの定番

CAP定理：分散システムでは、一貫性、可用性、分断耐性のすべてを同時に完全には満たせない、という定理です。

冪等性：同じ操作を何度実行しても結果が変わらない、という性質です。

フェイルセーフ：失敗しても安全側に倒す、という考え方です。

フループループ：人が間違えても危険な状態になりにくいように、操作や設計でミスを起こしにくくする考え方です。

結果整合性：すぐには一致しないが、時間が経てば整合する、という考え方です。書き込み直後に読み込むと古い値が見えるかもしれないが、しばらくすれば一致する、という性質です。

フェイルファスト：問題があるなら早く失敗させる、という考え方です。

バックプレッシャー：受け手が処理しきれないとき、送り手を抑制する仕組みです。

Graceful degradation：一部が壊れても、全体をできるだけ動かす、という考え方です。
