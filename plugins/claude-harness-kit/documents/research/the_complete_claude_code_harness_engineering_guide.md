## なぜハーネスが必要なのか

AIモデルそのものを賢くするよりも、周囲の「環境（ハーネス）」を整える方がはるかに重要。

- **実績**: LangChainの実験では、モデルは一切変えずハーネスだけを改善することで、Terminal Bench 2.0のスコアが **52.8% → 66.5%** へ +13.7ポイント向上（LangChain Blog, 2026年2月）
- この +13.7pt は単一レイヤーでは説明できず、**コンテキスト注入（レイヤー1）・自己検証ループ（レイヤー5）・計算割り当て（レイヤー5）の3レイヤー協働**によって達成された
- 多くのClaude Codeユーザーはレイヤー1で止まっており、残り4層が手付かずのまま

**核となる定式（Martin Fowler, 2026年4月）:**

```
Agent = Model + Harness
```

モデルはコモディティ。Sonnet 4.6やOpus 4.7を使うどのチームも同じ素の能力を持つ。差を生むのはハーネス。

**助言 vs 強制の対比:**

- CLAUDE.mdに「本番データベースを削除するな」と書く → AIが大量の文脈を処理するうちに **無視される危険がある（助言）**
- PreToolUseフックでブロックする → AIが**回避できない強制**になる

## 5つのレイヤー

| レイヤー | 役割 | Claude Codeでの実装 |
|---|---|---|
| **1. Memory（記憶）** | 何を知っているか | `CLAUDE.md`, `MEMORY.md`, `.claude/commands/` |
| **2. Tools（ツール）** | 何に到達できるか | MCP（Model Context Protocol）サーバー |
| **3. Permissions（権限）** | 何を許されているか | `settings.json` の allow / deny リスト |
| **4. Hooks（フック）** | 実行時に何が強制されるか | `PreToolUse` / `PostToolUse` フック |
| **5. Observability（可観測性）** | 事後に何が見えるか | セッションログ、コスト追跡、アクション監査 |

---

## Layer 1: Memory（最初のキー入力の前に知っていること）

- **CLAUDE.md**（静的ルール）: プロジェクトの基本ルールを記載。**40〜60行に抑えるのがベスト**
- **MEMORY.md**（動的な状態）: 進化する状態・過去の判断を保持する約200行のインデックス（設定5分）

**失敗ログパターン（Ghostty AGENTS.mdより）:**
GhosttyのAGENTS.mdには願望的な行が一つもなく、各エントリが**実際のエージェントのミスに遡れる**。理想論の指示ではなく、リアルな失敗をベースに制約ルールをアップデートし続ける。

**Failure-to-Constraint 決定木（どこに記録するかの判断基準）:**

| ケース | 置き場所 |
|---|---|
| 危険な操作（本番DB削除など） | → Hooks |
| 繰り返すワークフロー | → Commands（`.claude/commands/`） |
| スタイル・コーディング規約 | → CLAUDE.md |

---

## Layer 4: Hooks（エージェントが「できない」こと）

フックは**強制レイヤー**。メモリは助言、フックは法。

- **PreToolUseフック**を終了コード2で終了させると、Claude Codeのコマンド実行を問答無用でブロック
- Claude Code内で**唯一ツール呼び出しを無条件にブロックできる**仕組み

4つのフックハンドラー型:

| ハンドラー | 用途 |
|---|---|
| **Deny（拒否）** | 危険なコマンドをブロック（例: 本番でのDROP TABLE） |
| **Log（記録）** | 操作の証跡を残す |
| **Transform（変換）** | 出力を安全な形式に変換 |
| **Enrich（補完）** | コンテキストを追加してモデルに渡す |

**PreToolUse vs PostToolUse の使い分け**: 実行前にブロックしたいなら PreToolUse、実行後の結果を検証・記録するなら PostToolUse。

---

## Layer 5: Observability（エージェントが実際に何をしたか）

可観測性は「エージェントが変なことをした」を**再現可能なバグレポートに変える**。

- LangChainの改善の一つは、タスク完了とマークする前にエージェントに自分の仕事を検証させる**検証ミドルウェア**だった
- Boris Cherny（Claude Code作者）は検証を品質にとって「おそらく最も重要なこと」と述べている
- **自己検証ループ**: `/done` コマンドでAIがタスク完了時に自動チェックリストを走らせる実装が有効

## 構築の「正しい順番」

```
1. Memory（CLAUDE.md + MEMORY.md） → 基本ルールと状態を定義
       ↓
4. Hooks（PreToolUseガード1つ）   → 危険な操作を先にブロック
       ↓
2. Tools（MCP、2〜3個に絞る）     → 能力を追加（5個以上はノイズ）
       ↓
3. Permissions                    → 安全な境界線を引く
       ↓
5. Observability                  → ログ・コストを追跡
```

最初から5層すべては不要。**Memory + Hooks の2層だけで最も多い失敗モードをカバーできる。**

---

## 制約のパラドックス（The Constraint Paradox）

能力より制約が勝つことを示す3つのデータ点:

1. LangChainのハーネス変更のみで +13.7pt（モデル変更なし）
2. OpenAI Codexは強く制約されたハーネス環境内で約100万行の本番コードを人間の手書きゼロで生成（2026年2月）
3. GhosttyのAGENTS.mdは全行が**防いだ失敗**から生まれた記録

反直感的な発見: **推論予算を最大で走らせると53.9%、高設定なら63.6%** — 「モデルをより賢く動かせばいい」という直感を覆す。

## 3つのキーワードの区別（FAQ）

| 用語 | 何を制御するか |
|---|---|
| **プロンプトエンジニアリング** | 何を試みるか（AIへの指示） |
| **コンテキストエンジニアリング** | 何を知っているか（知識・状態の注入） |
| **ハーネスエンジニアリング** | 何ができ・できないか（フック・権限による強制） |

## シニアエンジニアの役割の変化

開発者の84%がAIツールを使うが、出力を信頼しているのは29%のみ（55ポイントの差）。この差を埋めることがシニアエンジニアの新しい仕事。

| 従来 | これから |
|---|---|
| 自分でコードを書くこと | AIエージェントが安全に自律駆動できる「ハーネス（環境）」を設計すること |

**チームへの波及効果**: バージョン管理にコミットした1つのハーネスはチーム全体に波及する。10人向けに優れたCLAUDE.mdを書くことは、自分で1万行のコードを書くより大きなリターンをもたらす。

## まとめ

**プロンプトを工夫する（AIにお願いする）段階**から、**システムとして制御する（ハーネスをエンジニアリングする）段階**へのステップアップが、2026年現在のAI開発における最重要スキル。

Agent = Model + Harness の定式のもと、モデルが同じでもハーネス次第で再現性が激変する。5層のうちまず Memory と Hooks の2層から着手し、それぞれ CLAUDE.md + MEMORY.md と PreToolUse ガード1本を整えることが最短の出発点。
