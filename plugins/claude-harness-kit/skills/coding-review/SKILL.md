# coding-review

## 概要

対象コードの変更を分析して frontend / backend を判定した上で、コーディング規約・
テスト規約（frontend の場合は追加で UI デザイン）の観点で専門サブエージェントへ
横断レビューを委譲する統合エントリスキル。**指摘までが責務**で、コードの改善・適用は
行わない。判定した domain に対応する専用サブエージェントが無い場合は、本スキル自身が
[[design-rule]] に基づき推論でレビューするフォールバックを標準の方針とする。

## 手順

### 1. レビュー対象を確定する

デフォルトは **git 変更差分**。`git status` と `git diff`（未コミット）＋
`git diff main...HEAD`（main との差分）で変更ファイルを把握する。
ユーザーがファイル・ディレクトリを明示した場合はそちらを優先する。

### 2. domain を判定し、観点ごとに振り分ける

| domain | コーディング規約 | テスト規約 | UI デザイン |
|--------|----------------|-----------|------------|
| frontend | `frontend-code-reviewer` | `frontend-test-reviewer` | `ui-reviewer` |
| backend | `backend-code-reviewer` | `backend-test-reviewer` | 対象外（backend に UI 観点は無い） |
| 専用サブエージェント無し | 本スキル自身が [[design-rule]] に基づき推論でレビュー | 同左 | 対象外 |

対象がある観点だけを起動する。実装コード（`.ts`/`.tsx`/hooks/ユーティリティ等）は
コーディング規約（＋frontend なら UI デザイン）、テストコード（`*.test.*`/`__tests__/`等）は
テスト規約の観点に振り分ける。

### 3. 専門エージェントへ委譲する（並行）

独立しているため並行で投げてよい。各エージェントには「レビュー対象ファイル／差分」と
「指摘のみ・修正は適用しない」旨を渡す。専用サブエージェントが無い domain の観点は、
本スキル自身が in-context でレビューする。

### 4. 所見を統合する

各エージェント（および本スキル自身によるフォールバックレビュー）の返り値を観点ラベル付きで束ね、重複を排除し、優先度（Critical / Warning / Suggestion）で並べ替える。

## 出力

観点（コーディング規約 / テスト / UIデザイン）ごとにセクション分けし、各セクション内を
優先度順で示す。**修正の適用は行わない**（適用は産出者に委ねる旨を添える: コード・テストの
実装は `coding` / `test-coding` スキル、UI は `ui-review` 経由の `ui-designer`）。

3段階（Critical / Warning / Suggestion）の定義は [[severity-rule]]（`shared-rules/review-severity/severity-rule.md`）に従う。このドメインの Critical 該当例: 動作・規約・UXを大きく損なう重大な問題。

各項目は `file:line` ／ 違反した規約（根拠ルールのパス、フォールバック時は依拠した一般原則）／ 問題点 ／ 修正の方向性 の形で示す。全観点で違反がなければ「規約準拠で問題なし」と明記する。
