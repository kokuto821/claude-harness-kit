# tdd

## 概要

`tdd-rule` を唯一の根拠に、TDD サイクルの各フェーズを適切な産出者・レビュアーへ委譲する。
List/Red/Green/Refactor はいずれも domain（frontend/backend 等）を問わない単一の入口スキル
（`test-coding` / `coding` / `coding-review`）へ委譲し、domain 判定と具象サブエージェントへの
分岐は各入口スキル側の責務とする。tdd スキル自身は domain の詳細には関与せず、フェーズの
進行のみを統括する。指摘の適用はレビュー独立性に従い産出者が担う。

## ルール

- サイクル（List-Red-Green-Refactor-Commit）とコーディング標準は [[tdd-rule]]（`shared-rules/coding-conventions/tdd-rule.md`）に従う。「Red-Green-Refactor」は通称であり、正確には List を含む5フェーズである（[[tdd-rule]] §2）。フェーズを飛ばさず、現フェーズ（LIST/RED/GREEN/REFACTOR/COMMIT）を常に明示する。
- レビューと修正適用の分離は [[review-independence-rule]] に従う。Refactor のレビューも産出者と別エージェントが行い、適用は産出者に戻す。
- **産出者の単一責任**: List/Red は `test-coding` スキル、Green は `coding` スキルの責任。各スキルは自身の担当フェーズのみを担い、他フェーズの産出や自己完結はしない。
- **隔離（サブエージェント委譲）の理由は2種類あり、混同しない**:
  - **産出フェーズ（List/Red/Green）の隔離**: [[selection-rule]] の「隔離したい副次タスク」基準による。テスト・実装の試行錯誤はメイン会話を汚しやすいため、`test-coding` / `coding` スキルは in-context で起動しつつ、実際のコード生成は domain 判定の上で専用（または汎用）サブエージェントへ隔離委譲する（[[domain-classification-rule]]）。最終的な実装・テストコードの結果だけを確認できればよく、生成過程の逐次可視性は要求しない、という判断（issue #17 で明示的に承認済み）。
  - **Refactor フェーズの隔離**: [[review-independence-rule]] による。産出者本人には自作物の甘さ・盲点があるため、産出者とは別エージェントにレビューさせる。「メインを汚すから」ではなく「自己評価を信頼しない」ことが理由。
  - 両者は理由が異なるため、一方の説明を他方に流用しない。
- **委譲の種別を区別する**: 「エージェント委譲」＝別コンテキストで隔離起動（中間結果でメインを汚さない）、「スキル起動」＝現行コンテキストで in-context 実行。`test-coding` / `coding` / `coding-review` はいずれも tdd から in-context で起動し、各スキル内部が domain 判定の上で具象（または汎用）サブエージェントへ隔離委譲する。
- **反復上限**: 1機能あたり最大 3 サイクルを目安とする。3 周で緑にならない／未解決が残る場合は、サイクルを続けず、達成範囲と残課題を報告して人の判断を仰ぐ。これは対話の中で守る目安であり、ハーネスによる強制ではない（暴走はメインスレッドで可視・中断可能）。上限を確実に強制したい場合のみ、commit を捕捉する hook を別途用意する。
- **Refactor の停止条件**: レビュー→適用は 1 ラウンドで打ち切る。追加の指摘が残る場合は次サイクルの Refactor へ送る。
- **サイクルをまたぐ記憶**: 決定・未解決事項・次サイクルの狙いを、スクラッチパッドの `tdd-notes.md` に数行で退避し、次サイクル冒頭で読み直す（[[long-horizon-rule]]）。
- 規約の具体値は再掲せず、上記ルールを唯一の正として参照する（[[externalization-rule]]）。

## 手順

1. **List — テストリストを洗い出す** / **Red — 失敗するテストを書く**
   - `test-coding` スキルを in-context 起動。同スキルが検証すべき振る舞いのシナリオを洗い出し（List。[[tdd-rule]] Phase 0）、リストから1項目を選んで失敗するテストを実装する（Red。[[tdd-rule]] Phase 1）。「失敗するテストのみを実装し、実装コードは書かない」と明示する。Red の実装段階では同スキル内部で domain 判定の上、対応するサブエージェント（例: `frontend-tester` / `backend-tester`、専用サブエージェントが無い domain は汎用サブエージェント）へ隔離委譲される（[[domain-classification-rule]]）。テストが RED であることを確認する。
2. **Green — テストを通す最小実装**
   - `coding` スキルを in-context 起動。テストは Red で用意済みのため実装のみ。同スキル内部で domain 判定の上、対応するサブエージェント（例: `frontend-coder` / `backend-coder`、専用サブエージェントが無い domain は汎用サブエージェント）へ隔離委譲される（[[domain-classification-rule]]）。テストを通す最小限にとどめ、余分な機能を足さない。全テストが GREEN になることを確認する。
3. **Refactor — レビュー主導の改善（緑を保つ）**
   - `coding-review` スキルを in-context 起動。同スキル内部で domain 判定の上、コーディング規約・テスト規約（frontend なら追加で UI デザイン）の観点で該当レビューサブエージェントへ隔離委譲され、指摘のみ返る。指摘を受け、産出者（`coding` / `test-coding` が委譲した実装・テスト）が全テスト緑を維持したまま **1 ラウンド**適用する。残る指摘は次サイクルの Refactor へ送る。
4. **反復** — テストリストが空になるまで手順1〜3を繰り返す（[[tdd-rule]] Phase 4）。反復上限（ルール「反復上限」）に達していなければ、リストの次の項目で手順1へ戻る。
5. **Commit — チェックポイントを記録**
   - 全テストが緑であることを最終確認（テスト実行で担保。[[review-independence-rule]]: 再検証も産出本人に委ねない）→ `git add` → 意味ある単一作業単位でコミットする。サイクルのノート退避（ルール「サイクルをまたぐ記憶」）を行う。
6. **次サイクルへ** — 機能が未完成でリストが空でなく、反復上限（ルール「反復上限」）に達していなければ、次サイクルへ戻る。上限に達したらルールに従い終了する。

## 出力

- 現フェーズ（LIST/RED/GREEN/REFACTOR/COMMIT）、委譲先（入口スキルと、判明していれば内部で分岐した具象サブエージェント）と結果、テストの緑/赤状態、コミット単位、サイクル番号（例: 2 周目）。
