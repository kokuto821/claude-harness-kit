# TDD（Test-Driven Development）ルール

このルールは、プロジェクトにおける TDD の核心哲学・開発サイクル・コーディング標準を定義する。Kent Beck の Canon TDD（t-wada 氏による解説 https://t-wada.hatenablog.jp/entry/canon-tdd-by-kent-beck）に基づく。テストを書く／TDD で進める場合は常にこのルールに従うこと。

## 1. 核心哲学: テスト駆動

TDD は以下の4つの状態にシステムを導くことを目的とする:

1. それまで動作していたものは引き続き全て動作する
2. 新しい振る舞いは期待通りに動作する
3. システムはさらなる変更の準備ができている
4. プログラマとその同僚は、上記に自信を持っている

- **テストが開発を駆動する:** プロダクトコードは失敗するテストを通すためにのみ書く。テストは後付けではなく、仕様であり設計のドライバーである。
- **リファクタリングへの自信:** 網羅的なテストスイートはセーフティネットである。安心して継続的にリファクタ・改善できる。
- **テスタビリティ＝良い設計:** テストしにくいコードは設計が悪い兆候。テストしやすいコードを優先することで、疎結合・高凝集なアーキテクチャに自然と導かれる（[[design-rule]]）。
- **TDD は手段であり目的化しない:** TDD の実践自体が正当性を生むわけではない。採用する手法が何であれ、仕事の質に責任を持つのはプログラマ自身である。

## 2. 開発サイクル: List-Red-Green-Refactor-Commit

「Red-Green-Refactor」という通称は不完全である。正確には「**リスト・レッド・グリーン・リファクタ**」。リストを省略すると開始条件・終了条件が曖昧になり、インクリメンタル設計が失われ、テスト項目を先にまとめて書いてしまう誤った実践を招く。

どんなに小さな変更でも、この反復サイクルに従う。コード生成時は現在どのフェーズかを明示すること。フェーズを飛ばすことは禁止。

### Phase 0: List — テストリストを洗い出す

- **目的:** 検証すべき振る舞いのシナリオを分析し、列挙する。
- **アクション:** 正常系の動作・エラーケース・エッジケース・既存機能への影響回避を洗い出し、リスト化する。
- **条件:** この段階では実装設計判断を混ぜない。テストは「どう呼び出されるべきか」（インターフェース設計）と「どう実装するか」（実装設計）に分かれ、後者は Phase 3（Refactor）で扱う。
- **リストは固定ではない:** 作業中に新しい項目に気づいたら随時リストへ追加する。既存の設計との矛盾が判明した場合は、リストを見直す判断をする。

### Phase 1: Red — 失敗するテストを書く

- **目的:** リストから1項目を選び、その振る舞いのインターフェースを定義する。
- **アクション:** 準備・実行・検証（アサーション）を備えた自動テストを「1つだけ」書く。アサーションから逆算して書くとよい。
- **禁止事項:** リストの全項目を先にまとめてコード化しない／アサーションのないテストで済ませない／期待値としてテスト対象の出力をそのまま貼り付けない（ダブルチェックの意味が失われる）。
- **条件:** 対応する実装がまだ存在しないため、このテストは失敗する（**RED**）こと。

### Phase 2: Green — テストを通す

- **目的:** 選んだテストが定義した要件を満たす。
- **アクション:** 失敗するテストを通すための最小限のコードを書く（**GREEN**）。リファクタと同時に行わない（「まず動かし、その後に正しくする」の順序を守る）。
- **条件:** 余分な機能を足さない。この段階で優雅さは目標ではなく、テストを通すことだけが目標。
- **Green 到達時:** 新しいテスト項目に気づいたらリストに追加する。既存設計との矛盾が判明した場合は見直す判断をする。

### Phase 3: Refactor — 設計を改善する

- **目的:** 全テストを緑に保ったまま、ここで初めて実装の設計判断を行う。
- **アクション:** 通るテストの安全のもとで内部構造を改善する。重複除去（DRY）・命名改善・複雑なロジックの単純化・下記コーディング標準の充足など。設計原則は [[design-rule]] に従う。
- **禁止事項:** 次のテストへの不安からの逃避としての過剰なリファクタ／重複を早すぎる抽象化の指令として扱う（重複はヒントであり指令ではない）。
- **条件:** リファクタリング中も全テストが **GREEN** であり続けること。

### Phase 4: 反復

テストリストが空になるまで Phase 1〜3 を繰り返す。コードの動作に対する不安が退屈に変わるまで続ける。

### Phase 5: Commit — 進捗を保存する

- **目的:** 機能する小さな作業単位を安全なチェックポイントとして記録する。
- **アクション:** リファクタ完了後、全テストが緑であることを最終確認し `git add .` でステージする。次のサイクルへ進む前の安定したチェックポイントとなる。
- **条件:** 変更は単一の意味ある作業単位であること。コミットメッセージもその作業を簡潔に記す。

## 3. 厳格なコーディング標準と禁止事項

### 【CRITICAL】ハードコーディング禁止

いかなる形式のハードコードされた値も厳禁。

- **マジックナンバー:** ロジック中に数値リテラルを直接書かない。名前付き定数として定義する。命名規則の具体（`UPPER_SNAKE_CASE` 等）は [[coding-rule]]（`shared-rules/coding-conventions/coding-rule.md`）に従う。
- **設定値:** API キー・URL・ファイルパス等の環境設定は設定ファイル（`.env`, `config.js` 等）や環境変数から読み込む。ソースコード中に存在させない。
- **ユーザー向け文字列:** UI・ログ・エラーのテキストは定数や localization ファイルで管理し、保守性と国際化に備える。

### その他の主要標準

- **設計原則:** [[design-rule]]（`rules/design-principles/design-rule.md`）に従う。
- **明確で意図的な命名:** 変数・関数名はその目的と意図を明確に伝える。
- **ガード節 / 早期リターン:** 深いネストを避けるため早期リターンを優先する。
- **セキュリティ第一:** ユーザー入力は常に信頼しない。XSS や SQL Injection を防ぐため入力をサニタイズし出力をエンコードする。
