# ハーネス制御の媒体選択ルール

## 原則

**コードで書けるものはコードで書く。Markdown には書けないものだけを `.md` に書く。**

| 媒体 | 向いているもの | 向いていないもの |
|------|--------------|----------------|
| `.sh` / `.ts` / `.js` | 保証・強制・決定論的制御 | モデルへのソフトな指針 |
| `.md` (CLAUDE.md, rules/) | コンテキスト・方針・規約 | セキュリティや安全ガード |

## 判断基準：「破られたら困るか」

| 判定 | 例 | 置き場所 |
|------|----|----------|
| 破られたら困る（安全・課金・データ破壊系） | `rm -rf` ブロック、パーミッション制限、リトライ上限 | コード（`.sh` / `.ts` / `.js`） |
| 破られても許容できる（スタイル・文脈系） | コーディング規約、出力のトーン、ライブラリの好み | Markdown（`.md`） |

## なぜコードに置くのか

Markdown はモデルが「読んで解釈する"お願い"」にすぎない。実行セマンティクスがなく、
prompt injection によって賢いモデルほど説得・回避しうる。

コードは、モデルがどう振る舞おうと迂回できない。セキュリティ・制御の核心部分では
「より良い」ではなく、**保証を与えられる唯一の手段**である。

## 具体的な使い分け

### コード（`.sh` / `.ts` / `.js`）に書くもの

- パーミッション判定・deny リスト（許可していないツール呼び出しのブロック）
- フック処理（pre-commit, post-tool など）の実行ロジック
- リトライ・トークン管理・状態マシンのループ
- 環境変数の検証、シークレットの存在チェック
- 自動化スクリプト（定型操作のシェルスクリプト化）

### Markdown（`.md`）に書くもの

- プロジェクトの方針・背景・目標
- コーディング規約・ライブラリの選好
- 出力フォーマット・トーンの指針
- 「なぜ」の説明（コメントより CLAUDE.md が適切な場合）
- モデルの判断を「導く」ための文脈

## 適用手順

1. 追加しようとしている指示・制御を確認する
2. 「破られたら困るか」で判定する
3. 困る → コードファイルとして実装する（hooks、スクリプト、settings.json）
4. 困らない → `.md` に記述する
5. 両方の要素が混在する場合は分割して書く
